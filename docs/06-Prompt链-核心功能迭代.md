# 核心功能迭代的完整 Prompt 链

> 本文档为参赛材料，从与 AI（WorkBuddy/CodeBuddy）的**原始开发会话记录**中原样摘录，展示六个核心功能从提出需求、AI 给出方案、到引导 AI 排查修复问题的完整交互过程。
> 对应的完整记录见 `prompts/`（分轮提示词脚本）；AI 调用的留痕原文可在管理端 `/admin/ai-logs` 在线查看与导出。

## 链一：申领流转状态机——测试先行的工程化起点（2026-11-14，R5）

### 用户 Prompt 原文

> 做收藏和申领流转。状态机单独一个文件（同意、拒绝、完成、取消四种动作，非法流转抛错），路由里不许散落 if。
> 捐赠物品完成交割时写捐赠台账，重量按类别系数折算。
> 越权一律 403。给状态机写测试。

注意这条 Prompt 里用户定的三条硬规矩：**状态机独立成文件、路由不许散落 if、越权一律 403**——把「业务正确性」从编码规范层面锁死。

### AI 的执行过程（回复节选）

> **AI：** 先解决一个技术前提：Node 22 的 `node --test` 能否直接跑 `.ts` 测试文件……两个类型错误要修：PATCH 路由的 `action` 类型、测试的 `.ts` 后缀导入。
> **AI：** Build and tests pass（13/13）。再跑一遍申请→同意→完成全流程的端到端集成测试，覆盖捐赠台账与 403 越权。
> **AI：** All 12 integration checks pass —— 捐赠台账写入 `green_weight_kg=2.5`（被褥类系数），越权返回 403。

### 结果与沉淀

- `src/server/item-state.ts`：纯函数 `transition(item, application, action)`，四种动作 + 非法流转抛错，路由层零 `if` 判断
- `src/lib/green-factors.ts`：类别重量系数与 `greenWeightKg()` 折算，后来整个环保看板复用
- `tests/item-state.test.ts`：13 个用例（正常链路 + 非法流转 + 越权），此后每轮新功能测试数持续增长至 228
- 「先写测试再动路由」的模式从此成为项目惯例

## 链二：发布前审核——词表 + 模型双路，故障不能变成放行漏洞（2026-11-14）

### 用户 Prompt 原文

> 做发布前审核：判定违禁品、危险品、药品、活体、不良内容、疑似校外倒卖，返回是否通过、类别、理由。
> 再加一层本地关键词兜底。模型故障时不能变成放行漏洞——放行但要标记待人工复核。
> 管理员端做复核队列，可下架或恢复。

这条 Prompt 最关键的一句是**「模型故障时不能变成放行漏洞」**——用户主动要求把 AI 的失效模式纳入安全设计。

### AI 的方案与真实故障演练（回复节选）

> **AI：** 收到。先摸清现有结构：物品表字段、发布接口、管理员端现状、AI 调用底座……Schema 里已经预置了 `violation_flag` / `violation_reason`，不用改表，开始实现。
> **AI：** 测试环境不支持 `@/` 别名，我把判定模块写成零运行时依赖，才可能被单测直接跑。
> **AI：** 模型侧挂了——百炼账号欠费（`overdue payment`）。**这恰好把「故障降级」路径真实跑通了**，但要验证正常判定路径还得用本地 mock 端点。先写 mock。

### 结果与沉淀

两层判定、严格优先（`src/lib/banned-terms.ts` + `src/lib/ai/moderate.ts`）：

| 层 | 作用 |
|---|---|
| 本地词表 6 类 | 违禁品 / 危险品 / 药品与医疗器械 / 活体动物 / 不良内容 / 疑似校外倒卖。纯字符串匹配不依赖网络，**模型挂了也拦得住硬违规** |
| 模型判定 | 有图走多模态、无图走文本，45 秒超时退回纯文本判定 |

模型故障时**放行 + 打待复核标记**（不是拦截也不是裸放行），管理员端 `/admin/violations` 复核队列可下架可恢复——用户要求的失效安全（fail-safe）落地为机制。

## 链三：VLM 拍照识图发布与模型故障排查（2026-11-14 → 11-15）

### 第一问：搭 AI 调用底座（R9）

> **用户 Prompt 原文：**
> 做 AI 调用层：统一封装 chat 与 embed，15 秒超时，错误区分 api_error、timeout、parse_error。
> 所有 prompt 集中放一个文件。每次调用把 prompt 原文和模型原始返回……

### 第二问：接发布页 AI 辅助（R10）

> **用户 Prompt 原文：**
> 接发布页的 AI 辅助：图片和一句话描述进去，类别、成色、标题、文案、标签出来，强制 JSON 输出，禁止编造图片里没有的品牌型号。
> 回填后 AI 填过的字段标「AI」徽章，用户改动后变「已修改」。
> 模型不可用时退回手动……

**过程中的真实故障**：API 连续返回 `402 Insufficient Balance`，同一指令重试 7 次（会话记录原样保留）。AI 没有绕过错误：

> **AI：** 当前百炼与 DeepSeek 的 key 都返回 401，我起一个本地 mock 模型端点来验证「成功路径」（组 prompt → 多模态 → 解析 → 留痕）是否真的通。

即先用 mock 打通全链路，把「接口能用」和「账号能用」两个问题解耦。

### 顽固 Bug：识图模型全体报错（11-15）

上线后识图链路突然全挂，用户两次纠正 AI 的猜测方向：

> **用户**（发来账单截图）：不是充钱
> **用户**：开了延迟服务
> **用户**（再发账单截图）：没欠费

**AI 的排查**（会话记录原样节选）：

> **AI：** 先别猜，直接看这个 key 现在到底报什么。……三种模型返回的居然是三种不同错误，这不像是单纯欠费。
> **AI：** 抱歉，我上一轮的说法有误：问题并不在于「余额为 0」……假 key + qwen-plus 返回 `401 invalid_api_key` 说明鉴权链路是通的；qwen-plus / qwen-max 返回 `400 Arrearage` 是账号级拦截。
> **AI：** `/models` 返回 200，说明 key 有效、服务可访问，这印证了「确实没有欠费」。既然能列出模型目录，我就从目录里找可用的模型……有突破：`qwen3.5-ocr` 返回 200 ok，`qwen3.7-text-embedding` 也返回 200、1024 维。
> **AI：** 视觉请求超时了，因为图片有 431KB，太大。我改用小图再试，并同时验证纯文本 JSON 输出。

**最终修复**：定位可用模型组合（`qwen3.8-omni-flash` 多模态 + `qwen3.7-text-embedding`）；大图先降采样再送模型（`src/server/vision-image.ts`，长边 1280 / JPEG q82 / 按 EXIF 摆正）；omni 系是思考型模型，对短输出强约束 JSON 的调用统一传 `thinking: false`，识图延迟实测 **16.1s → 3.5s**。

**方法论沉淀**：错误分类法（鉴权 401 / 账号状态 400 / 限流 429 是三个不同层面）、mock 解耦、模型目录探测——全部写进 README 的「模型选择与降级」。

## 链四：AI 环保报告——数字白名单治理幻觉（2026-11-15，R18）

### 用户 Prompt 原文

> 做报告生成：统计结果喂给模型出 600-900 字图文报告，数字必须原样引用，服务端比对不通过就不展示。
> 支持打印导出 PDF，捐赠台账支持 CSV 导出。

「数字必须原样引用，比对不通过就不展示」是用户主动提出的约束——把 AI 幻觉治理从口号变成了机制。

### AI 的方案（回复节选）

> **AI：** 报告不是「生成出来就直接展示」的，中间加了一道服务端逐字比对：**数据区里没有的数字，一个都进不来**。
>
> 流程是 `SQL 聚合 → 数据快照 → 进 prompt → 模型写 → 服务端比对 → 通过才展示`。
>
> - **白名单即数据区**：`buildPayloadText()` 既拼出送进 prompt 的「数据」段，也是白名单的唯一来源。模型能写 `7.15`，因为它在那儿；写 `7.2` 判失败——那是四舍五入，不是原样引用。归一化只处理千分位/前导零/小数末尾零/全角数字，`7.10 = 7.1` 算通过。
> - **两项硬校验**：数字（未命中即 fail）+ 字数（去空白字符数 600–900）。最多两次，第二次 prompt 会点名「上一版 542 字，少于 600」「这些数字数据里没有」。

### 结果与证据

- 校验状态写库（`reports.verify_status`），**fail 时正文一个字都不渲染**，只展示说明卡——见实测截图 `docs/screenshots/admin-report-fail.png`，这张「失败样例」本身就是机制在跑的证据
- 失败调用同样进 AI 留痕（记 `parse_error`），留痕页失败率因此包含「模型答了但数字对不上」
- 报告页图表读生成时的 `snapshot_json` 快照而非实时数据，保证数字表、图表、正文说的必须是同一批数

## 链五：统一 UI 组件——设计令牌与机器守门（2026-11-15，R19）

### 用户 Prompt 原文

> 统一基础组件（按钮、卡片、徽章、输入、弹窗、提示、骨架、空态），全部用主题令牌不许写死色值。
> 补齐加载态、错误页、404、移动端底部导航和必要的无障碍属性。

「全部用主题令牌不许写死色值」——用户要求的是可执行的约束，而不是审美口号。

### AI 的执行（回复节选）

> **AI：** **颜色只剩一处定义**：`src/app/globals.css` 的 `@theme` 是全站唯一允许写颜色字面量的地方……半透明统一 `color-mix(in srgb, var(--color-x) N%, transparent)`，不再写 `rgba()`。
> **AI：** 质量门全绿：build 通过、tsc 0 错、lint 0 error（6 个 `no-img-element` warning 保留）、179/179 测试通过。

### 结果与沉淀

- 九个基础组件（`src/components/ui/`）：按钮五形态、卡片三层圆角四底色、原生 `<dialog>` 弹窗（Esc/焦点还原由浏览器负责）、表单控件自带 label 关联与 `aria-invalid`
- **机器守门**：`tests/design-tokens.test.ts` 扫描全部 ts/tsx，出现 `#hex`、`rgb()/hsl()`、Tailwind 默认调色板类名即测试失败——写死一个色值，`npm test` 当场红
- 加载/错误/404/移动端底部导航全套补齐，骨架与真实卡片同高、切换不跳

## 链六：支付通道——从「做不到」到收款码全链路（2026-11-15）

### 用户提出需求

> **用户 Prompt 原文：**
> 设置支付通道，支付方式可以为微信，支付宝

### AI 先给约束再给方案

> **AI：** 探查完了：**项目目前没有任何支付代码**。现在的成交流程是「申领 → 物主同意 → 交割完成」，钱怎么转完全在平台外私下进行。
>
> 先说一个绕不开的现实：**真实接入微信/支付宝商户支付做不到**——两者都要求营业执照 + 商户号 + API 密钥签名验签，学生个人申请不到资质。这个不是技术问题，是准入问题。
>
> 所以「支付通道」只有两种可行的落地方式：……

**用户决策**：「要」（选定收款码方案：买家扫物主本人的收款码线下转账，物主在平台确认收款后交割，平台不碰钱、只做记账）。

### 实施链（会话记录摘录，可见 AI 的执行与自查节奏）

> **AI：** 先探查四个关键实现点（迁移怎么加列、上传怎么走、complete 事务、seed 图片），确保设计贴合现有代码。
> **AI：** 修正 payout 路由里的 require 写法（ESM 环境不可用）。
> **AI：** 那条用例撞上了前置校验顺序（申领 2 还没被同意，先返回 NOT_APPROVED）。换成用已同意但无支付记录的申领 4。
> **AI：** 现有库的卖家账号还没有收款码（不能重跑 seed，会清掉你发布的数据）——手动补上演示收款码。
> **AI：** `loadPaymentContext` 缺了个类型断言，修。

### 联调期的 Bug 修复（引导过程还原）

浏览器自动化验证时支付面板定位失败：

> **AI：** 查 Modal 组件的实际结构……面板是原生 `<dialog>`，打开的才有 `open` 属性。修正定位。
> **AI：** 场景 1、2 已完整跑完（错误发生在场景 3——那笔申领已交割完成，没有支付按钮了）。

**结果**：桌面 + 移动端全链路实测通过（支付记录 `confirmed`，申领与物品均 `completed`），测试 198 → 228 项全绿，提交 `07640d8`（17 个文件，+1048 行）。「规避资金池合规风险」本身成为答辩可讲的设计决策。

## 六条链的能力覆盖

| 链 | 展示的协作能力 |
|---|---|
| ① 状态机 | 用户定义工程规范，AI 测试先行落地 |
| ② 审核双路 | 用户预判 AI 失效模式，AI 用真实故障演练降级路径 |
| ③ VLM 识图 | 多轮排错：mock 解耦、错误分类、模型目录探测、性能优化 |
| ④ 报告白名单 | 用户一句话约束 → AI 落成可验证的幻觉治理机制 |
| ⑤ 统一 UI | 软约束变硬约束：令牌 + 测试守门，机器代替人眼 |
| ⑥ 支付通道 | 约束下的方案取舍、实施自查、联调修复全流程 |
