## 链一：VLM 拍照识图发布（R9–R10 → 模型故障排查）

### 1.1 第一问：搭 AI 调用底座（2026-11-14，R9）

> **用户 Prompt 原文：**
> 做 AI 调用层：统一封装 chat 与 embed，15 秒超时，错误区分 api_error、timeout、parse_error。
> 所有 prompt 集中放一个文件。每次调用把 prompt 原文和模型原始返回……

**AI 回复要点**（节选）：

> R9 AI 调用底座与留痕已完成。
> `src/lib/ai/client.ts`：`chat({model,messages,maxTokens})` + `embed({model,texts,dimensions})`，用已装 openai SDK；`AbortController` 15 秒超时；错误抛 `AiError`……

### 1.2 第二问：接发布页 AI 辅助（2026-11-14，R10）

> **用户 Prompt 原文：**
> 接发布页的 AI 辅助：图片和一句话描述进去，类别、成色、标题、文案、标签出来，强制 JSON 输出，禁止编造图片里没有的品牌型号。
> 回填后 AI 填过的字段标「AI」徽章，用户改动后变「已修改」。
> 模型不可用时退回手动……

**过程中的真实故障**：API 连续返回 `402 Insufficient Balance`，同一指令重试了 7 次（会话记录 [57]–[69] 原样保留）。AI 没有绕过错误，而是：

> **AI：** 当前百炼与 DeepSeek 的 key 都返回 401，我起一个本地 mock 模型端点来验证「成功路径」（组 prompt → 多模态 → 解析 → 留痕）是否真的通。

即先用 mock 打通全链路，把「接口能用」和「账号能用」两个问题解耦，随后完成 `6a0e4fe` 提交。

### 1.3 顽固 Bug：识图模型全体报错（2026-11-15）

上线后识图链路突然全挂。用户两次纠正 AI 的猜测方向：

> **用户**（发来账单截图）：不是充钱
> **用户**：开了延迟服务
> **用户**（再发账单截图）：没欠费

**AI 的排查过程**（会话记录 [115]–[130] 原样节选）：

> **AI：** 先别猜，直接看这个 key 现在到底报什么。……三种模型返回的居然是三种不同错误，这不像是单纯欠费。
> **AI：** 抱歉，我上一轮的说法有误：问题并不在于"余额为 0"。我又完整测了一遍……假 key + qwen-plus 返回 `401 invalid_api_key` 说明鉴权链路是通的；qwen-plus / qwen-max 返回 `400 Arrearage` 是账号级拦截。
> **AI：** `/models` 返回 200，说明 key 有效、服务可访问，这印证了"确实没有欠费"。既然能列出模型目录，我就从目录里找可用的模型……有突破：`qwen3.5-ocr` 返回 200 ok，`qwen3.7-text-embedding` 也返回 200、1024 维。
> **AI：** 视觉请求超时了，因为图片有 431KB，太大。我改用小图再试，并同时验证纯文本 JSON 输出。

**最终修复**：定位到可用模型组合（`qwen3.8-omni-flash` 多模态 + `qwen3.7-text-embedding`），大图先降采样再送模型（`src/server/vision-image.ts`，长边 1280 / JPEG q82 / 按 EXIF 摆正）；随后发现 omni 系是思考型模型，对短输出强约束 JSON 的调用统一传 `thinking: false`，识图延迟实测 **16.1s → 3.5s**。

**方法论沉淀**（也是这轮引导出的经验）：错误分类法（鉴权 401 / 账号状态 400 / 限流 429 是三个不同层面）、mock 解耦、目录探测。全部写进了 README 的「模型选择与降级」。

## 链二：AI 环保报告——数字白名单治理幻觉（2026-11-15，R18）

### 2.1 用户 Prompt 原文

> 做报告生成：统计结果喂给模型出 600-900 字图文报告，数字必须原样引用，服务端比对不通过就不展示。
> 支持打印导出 PDF，捐赠台账支持 CSV 导出。

注意这条 Prompt 的关键约束是用户主动提出的：**「数字必须原样引用，比对不通过就不展示」**——把 AI 幻觉治理从口号变成了机制。

### 2.2 AI 的方案（回复节选）

> **AI：** R18 完成。报告不是「生成出来就直接展示」的，中间加了一道服务端逐字比对：**数据区里没有的数字，一个都进不来**。
>
> 流程是 `SQL 聚合 → 数据快照 → 进 prompt → 模型写 → 服务端比对 → 通过才展示`。
>
> - **白名单即数据区**：`buildPayloadText()` 既拼出送进 prompt 的「数据」段，也是白名单的唯一来源。模型能写 `7.15`，因为它在那儿；写 `7.2` 判失败——那是四舍五入，不是原样引用。归一化只处理千分位/前导零/小数末尾零/全角数字，`7.10 = 7.1` 算通过。
> - **两项硬校验**：数字（未命中即 fail）+ 字数（去空白字符数 600–900）。最多两次，第二次 prompt 会点名「上一版 542 字，少于 600」「这些数字数据里没有」。

### 2.3 结果与证据

- 校验状态写库（`reports.verify_status`），**fail 时正文一个字都不渲染**，只展示说明卡（哪几个数字不在白名单、字数差多少、数据区原文可折叠查看）——见实测截图 `docs/screenshots/admin-report-fail.png`，这张「失败样例」截图本身就是机制在跑的证据。
- 失败调用同样进 AI 留痕（`ai_call_logs` 记 `parse_error`），留痕页的失败率因此包含「模型答了但数字对不上」，比只统计网络失败更有意义。
- 报告页图表读生成时的 `snapshot_json` 快照而非实时数据，保证「数字表、图表、正文说的必须是同一批数」。

## 链三：支付通道——从「做不到」到收款码全链路（2026-11-15）

### 3.1 用户提出需求

> **用户 Prompt 原文：**
> 设置支付通道，支付方式可以为微信，支付宝

### 3.2 AI 先给约束再给方案

> **AI：** 探查完了：**项目目前没有任何支付代码**。现在的成交流程是「申领 → 物主同意 → 交割完成」，钱怎么转完全在平台外私下进行。
>
> 先说一个绕不开的现实：**真实接入微信/支付宝商户支付做不到**——两者都要求营业执照 + 商户号 + API 密钥签名验签，学生个人申请不到资质，竞赛项目也没有主体资格。这个不是技术问题，是准入问题。
>
> 所以「支付通道」只有两种可行的落地方式：……

**用户决策**：「要」（选定收款码方案：买家扫物主本人的收款码线下转账，物主在平台确认收款后交割，平台不碰钱、只做记账）。

### 3.3 实施链（会话记录 [342]–[371] 摘录，可见 AI 的执行与自查节奏）

> **AI：** 先探查四个关键实现点（迁移怎么加列、上传怎么走、complete 事务、seed 图片），确保设计贴合现有代码。
> **AI：** 修正 payout 路由里的 require 写法（ESM 环境不可用）。
> **AI：** 那条用例撞上了前置校验顺序（申领 2 还没被同意，先返回 NOT_APPROVED）。换成用已同意但无支付记录的申领 4。
> **AI：** 现有库的卖家账号还没有收款码（不能重跑 seed，会清掉你发布的数据）——手动补上演示收款码。
> **AI：** `loadPaymentContext` 缺了个类型断言，修。

### 3.4 联调期的 Bug 修复（引导过程还原）

浏览器自动化验证时支付面板定位失败，AI 的排查：

> **AI：** 查 Modal 组件的实际结构……面板是原生 `<dialog>`，打开的才有 `open` 属性。修正定位。
> **AI：** 场景 1、2 已完整跑完（错误发生在场景 3——那笔申领已交割完成，没有支付按钮了）。

**结果**：桌面 + 移动端全链路实测通过（支付记录 `confirmed`，申领与物品均 `completed`），测试 198 → 228 项全绿，提交 `07640d8`（17 个文件，+1048 行）。「规避资金池合规风险」本身成为答辩可讲的设计决策。
